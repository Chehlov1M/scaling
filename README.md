# Задание 1. Преимущества масштабирования

Активный master-сервер и пассивный репликационный slave-сервер

Этот подход (активный мастер + пассивный слэйв) фокусируется на отказоустойчивости и резервном копировании.

Основные преимущества:

- Защита от потери данных. Если мастер выходит из строя, пассивный слэйв уже содержит актуальную копию данных (с минимальным отставанием). Это позволяет быстро переключиться на резервный сервер без потери информации.
- Минимизация простоев. Переключение на резервный сервер (failover) занимает считанные секунды, что критично для бизнес-критичных систем.
- Разгрузка мастера для бэкапов. Бэкап можно делать не с основного сервера, а со слэва. Это снимает нагрузку с мастера, который отвечает за обработку транзакций.
- Возможность аварийного восстановления. Слэйв можно использовать как «точку отката» при случайном удалении данных или повреждении.
- Упрощённое администрирование. Конфигурация обычно проще, чем при множестве узлов, а логика репликации прозрачна.

Master-сервер и несколько slave-серверов

Этот подход расширяет преимущества первого, добавляя масштабирование нагрузки (read scaling).

Основные преимущества:

- Распределение нагрузки чтения. Запросы SELECT (чтение) можно направлять на слэвы, разгружая мастер, который занимается в основном INSERT, UPDATE, DELETE. Это позволяет обслуживать больше пользователей.
- Гибкость масштабирования. При росте нагрузки можно просто добавить ещё один слэйв, не меняя архитектуру мастера.
- Географическое распределение. Слэвы можно разместить в разных дата-центрах или регионах, снижая задержку для пользователей (low latency).
- Отказоустойчивость кластера. Наличие нескольких слэвов повышает надёжность: если один узел упадёт, остальные продолжат обслуживать запросы.
- Аналитика и отчёты. Тяжёлые аналитические запросы можно запускать на слэвах, не мешая операционным процессам на мастере.
- Резервирование данных в разных зонах. Снижается риск потери данных из-за сбоя в одной локации.


# Задание 2. План для горизонтального и вертикального шаринга базы данных

Принципы построения системы

Вертикальный шаринг (Vertical Sharding) — разбиение по таблицам. Каждая таблица живёт в своей собственной базе данных (или на своём сервере). Это позволяет изолировать нагрузку по типам сущностей.

Горизонтальный шаринг (Horizontal Sharding) — разбиение внутри каждой таблицы по ключу (например, по ID или географическому признаку). Это нужно, если одна таблица становится слишком большой для одного сервера.
Разбивка по таблицам (Вертикальный шаринг)

Мы выделяем каждую таблицу в отдельную базу данных (и, возможно, на отдельный сервер):

1. База данных «Пользователи» (UsersDB)
        - Таблица: пользователи.
        - Назначение: авторизация, профили, личные данные.
        - Особенности: высокая частота операций INSERT/UPDATE (логины, смена паролей).
  
2. База данных «Книги» (BooksDB)
        - Таблица: книги.
        - Назначение: каталог товаров, метаданные (название, автор, жанр, цена).
        - Особенности: большой объём данных, частые запросы SELECT (поиск книг).
  
3. База данных «Магазины» (StoresDB)
        - Таблица: магазины.
        - Столбцы (произвольные): id, название, адрес, координаты, график_работы, количество_книг_на_складе, отдел_новинок.
        - Назначение: информация о точках продаж, складские остатки.
        - Особенности: связь с логистикой, частые обновления остатков.

Горизонтальное разбиение (внутри каждой БД)

Для каждой выделенной базы данных применяем шардинг по ID (или географическому признаку):

   - UsersDB: шардинг по user_id. Например, сервер UsersShardA хранит пользователей с id 1–1M, UsersShardB — 1M–2M.
   - BooksDB: шардинг по book_id. Сервер BooksShard1 — книги 1–50K, BooksShard2 — 50K–100K.
   - StoresDB: шардинг по store_id или по региону (например, StoresShardEU, StoresShardUS).

Режимы работы серверов

1. Master-серверы (Writes)
        - Принимают все операции записи (INSERT, UPDATE, DELETE).
        - Являются «источником истины» для своего шарда.
        - Работают в режиме высокой доступности.
2. Slave-серверы (Replicas / Reads)
        - Подключены к Master через репликацию.
        - Служат для чтения (SELECT) и балансировки нагрузки.
        - Могут быть географически распределены для снижения задержки.
        - Обеспечивают отказоустойчивость (failover).
3. Балансировщик нагрузки (Load Balancer / API Gateway)
        - На уровне приложения или сети направляет запросы в нужную базу (UsersDB/BooksDB/StoresDB).
        - Внутри каждой базы распределяет запросы по шардам.
        - Скрывает сложность топологии от конечного разработчика.
